### Engineering rules governing both quarters

These are stated once and apply to every migration, function and route in Q1 and Q2 alike.

- **Migration numbers are claimed at merge, never at plan or branch time**, against `max(version)` in `schema_migrations` **and** `origin/main`, and announced to concurrent sessions. This section therefore gives migration **counts and contents, not numbers** — a number written into a roadmap is a number claimed nine months early, which is precisely what made PRs #162 and #163 both ship a `00183`, made `db push` print "up to date", exit 0 and skip the file, and then broke the deploy workflow twice.
- **A green `Deploy DB Migrations` is not evidence a migration ran.** `supabase db push` keys on the version **prefix**. Every migration's effect is verified by reading the affected table back, mechanised by the `-- @verify:` header convention and `scripts/verify-migration-applied.ts` built in item 1.
- **Every new function in an exposed schema** is `SECURITY DEFINER` with no `current_user` in any authorisation decision, carries `REVOKE ALL ... FROM PUBLIC` **and** an explicit revoke for `anon`, and is verified with `has_function_privilege('anon', oid, 'EXECUTE')` — never by reading `proacl`. `field.allocate_form_no` was executable by `anon` in production because `GRANT ... TO service_role` restricted nothing (`apps/edge-functions/supabase/migrations/00179_site_forms.sql:317,326`).
- **Page-level gating is not a gate.** Every new surface is gated in the app *and* in the DB with RESTRICTIVE policies, because server actions and `app/api/*` routes are directly invocable and sit outside `(admin)/layout.tsx`.
- **`docs/rbac-matrix.md` moves in the same PR as every new route or endpoint, in both quarters**; `CONFORMANCE.md` moves with every auth-surface change. The route inventory and its route groups are Appendix A(g).
- **Every new edge function ships with a CLI deploy, a Management-API cron entry where it is scheduled, and an entry added to `.github/workflows/deploy-edge-functions.yml` in the same PR.** That workflow is `workflow_dispatch`-only and names exactly four functions (`.github/workflows/deploy-edge-functions.yml:7-8,29-51`), one of which — `generate-report` — **has no directory** under `apps/edge-functions/supabase/functions/` (verified), so a dispatch run fails at that step today. Its header claims `SUPABASE_ACCESS_TOKEN` / `SUPABASE_PROJECT_REF` "aren't bound" (`:3-6`), while `deploy-migrations.yml:7-9` records those two secrets plus `SUPABASE_DB_PASSWORD` as **bound 2026-06-02** — the edge-function header is stale, and item 0 settles which is true by re-reading them. Editing either file needs a `workflow`-scoped GitHub token. This is the documented cause of `cloud-sync-poll` never running at all despite shipping in a migration. **Q1 introduces no new edge function at all** — item 7's recap and item 4's dispatcher are Next route handlers — so **no Q1 deliverable waits on that token**. Q2's two new functions do.
- **Verification walks the flow from the empty state a real user starts in**, never from a deep link into seeded data.

### The shell decision (settles every client-facing claim below)

`apps/web/src/app/(admin)/layout.tsx:29` redirects any `client_viewer` to `/portal`, and `apps/web/src/app/(portal)/layout.tsx:22` redirects every non-`client_viewer` to `/dashboard`; the portal is read-only by construction — "server components with curated reads and no write actions" (`(portal)/layout.tsx:16-17`) — across twelve curated project pages. A page placed under `(admin)` is unreachable by a client, full stop.

**Decision: the Inbox and My Work move into a new shared route group `(work)` that sits beside `(admin)` and `(portal)`, gates on authentication only, and renders its own minimal shell** (Appendix A(g)). Role decides what is *in* the list, never whether the page renders. `(admin)/layout.tsx:29` and `(portal)/layout.tsx:22` are amended in the same PR so neither claims `/inbox` or `/my-work`. **The project home stays split** — `(admin)/projects/[id]` for staff, `(portal)/portal/[projectId]` for clients — with both rendering the same module-table component over one shared read; after the re-sequence that rebuild is **Q2 item 14**, not a Q1 deliverable. Rationale: the two-way fail-closed shell boundary is a deliberate, documented security property and is worth more than a single unified project page.

#### Risks

- **The critical path has 0.5 weeks of float and one person on it.** Items 0→1→2→4→5→6→7 are serial by design, not by staffing accident. *Mitigation: item 11 is already cut to buy the float that exists; the pre-window is protected for items 0 and 1 only; and if the path slips further the remedy is a second engineer inside item 4 — the one item with a separable dispatcher and preference surface — not a scope cut, because nothing else on the chain is cuttable.*
- **Arno's lane is fully loaded and every item but two is gated on the other lane.** The schedule above has zero idle from week 0 to week 9.17, so any slip in items 2, 4 or 5 pushes items 3, 13 and 10 out one-for-one, at 1.67 calendar weeks per engineer-week. *Mitigation: the lane is published as a schedule and re-read at each of the three gates (weeks 3.0, 6.0 and 7.5); item 14 is deliberately front-loaded because it is the only unblocked work, and item 10 — not item 3 — is the first thing to fall out, because the mirrors are what put anything in the Inbox at all.*
- **The December wall.** Work items land roughly six weeks before SA sites shut; a poor first impression then has a five-week dead zone before anyone re-opens the app. *Mitigation: contractor rollout starts in the last week of October on KINGSWALK only — one project, one PM assigning every item in the daily meeting — widening only on the November metric.*
- **The account estate may be worse than dormant.** If item 0 finds hard bounces or never-set passwords across most of the 13 contractor accounts, the recap has no channel and the Q1 outcome is unreachable as written. *Mitigation: item 0 runs three weeks before the window precisely so this is known before item 7 is designed; the fallback is WM re-inviting from verified addresses collected in the daily site meeting, which is slower but not blocked.*

#### Risks

- **Inbound email is now a Cloudflare dependency, not an entitlement gate.** The residual risk is a Worker misconfiguration silently dropping mail rather than a vendor saying no. *Mitigation: the Worker signs every forward and the function rejects an unsigned one, so a dropped message is a logged rejection rather than silence; and the Resend inbound answer from Q1 item 0, whenever it arrives, is a simplification that removes the hop entirely.*
- **iOS web push requires an installed home-screen PWA.** An iPhone user who never installs gets no push at all, and iOS is over-represented among WM staff. *Mitigation: install is part of the permission flow, and the 07:00 recap stays the guaranteed channel — push is an accelerant, never the delivery guarantee.*
- **Instructions are legal documents rendered through a WinAnsi-only font stack.** `≤ 0,2 Ω` printing as `d 0,2 ©` on a numbered instruction survives proofreading because it looks like a typo, not like corruption. *Mitigation: every payload string through `winAnsiSafe` (`apps/web/src/lib/pdf/winansi.ts`, `collapseWhitespace` false for react-pdf, true for pdf-lib) plus a byte-level decoded-stream assertion per new report kind — a fixture that cannot express the property under test makes the assertion decorative.*
- **One resolver guards eight subject types, and one of them now admits a client-viewer write.** A single wrong `CASE` arm shows a draft QC report to a client viewer, or accepts a message on a subject they should not see. *Mitigation: a contract test per subject type, run as a real `client_viewer` in a rolled-back transaction against production, failing the build when a new subject type has no arm.*
