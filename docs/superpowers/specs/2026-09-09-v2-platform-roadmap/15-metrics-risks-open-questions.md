## Success metrics, risks, rollout and open questions

### The measurement contract

**Decision: every headline number is computed in Postgres from first-party tables and written to an immutable weekly snapshot; PostHog is kept for exploration only and no metric may depend on it.** The reason is in the code. `getPostHogNode()` returns null the moment `NEXT_PUBLIC_POSTHOG_KEY` is unset (`apps/web/src/lib/analytics.ts:65-66`) and `trackServer` then returns without doing anything (`:80`, `:86`) — a missing environment variable and a quiet quarter produce byte-identical output, so no absence of data in PostHog can ever be interpreted. The catalogue also contains events nothing on the live surface emits: `SNAG_LOGGED` (`analytics.ts:43`) and `DIARY_ENTRY_CREATED` (`:48`) fire only from `apps/mobile/app/snags/create.tsx:76` and `apps/mobile/app/diary/[projectId].tsx:76` — an app never published, with zero push tokens in production. The sharpest illustration is `apps/web/src/actions/rfi.actions.ts:70`, which ships an `assignee_source` diagnostic specifically to reveal how many RFIs land unassigned: we cannot say what it recorded, because we cannot say whether it recorded. A metric whose absence and whose zero are indistinguishable is not a metric.

**One event stream, one snapshot store, one route — confirmed here and not re-opened.** `public.product_events` (§12 §(i)) is the append-only **event stream**; `projects.work_item_events` is the domain ledger the two elapsed-time metrics read; `public.platform_metrics_weekly` is the immutable **weekly snapshot store**; and **`/metrics` is the only route that renders it**. §13's `/team/metrics` is deleted — §04 cuts the `team` segment and no `team` directory exists under `apps/web/src/app` today (Appendix A(g), verified). `assignee_source` is re-emitted into `product_events` in the first Q1 migration's application change, because it is the one diagnostic that was built for exactly this question and has produced nothing usable.

**Presence is likewise confirmed, not re-opened.** `public.user_presence(user_id, last_active_at)`, `public.user_sessions(user_id, started_at, last_seen_at, user_agent, platform)` and the single writer `public.touch_presence(p_platform)` are the design §05 §(b) consumes and §12 §(i) cites; they are created here, in §15's Q1 metrics migration, and every other section reads them. §(b) below specifies them in full.

**A metric without a weekly audience is decoration.** The eight numbers are computed by a `pg_cron` job — `cron.schedule('platform-metrics-weekly', '0 4 * * 1', …)`, 04:00 UTC = 06:00 SAST Monday, no DST — into `public.platform_metrics_weekly`, following the inline-key `net.http_post` pattern the repo already uses (`apps/edge-functions/supabase/migrations/00148_floor_plan_versions_cloud_sync.sql:136-142`). They are rendered on `/metrics` and carried in the 07:00 recap. **The recap renders the previous week's snapshot row if this week's has not landed**, so a slow job degrades the number's freshness rather than blocking the send — and the missing row itself raises a `job_missed` notification under §(b2). Snapshot rows are append-only and carry `method_version`; changing a definition writes new rows rather than rewriting history — the same discipline as `read_at_estimated` in the notification backfill.

Seven of the eight are product metrics and run from Q1. **Metric 8 is the commercial one**: instrumented in Q1, deliberately zero until Q3, and it is the number the §(g) business case is answerable to.

`/metrics` uses `requireRolePage(OWNER_ADMIN)` (`apps/web/src/lib/auth/require-role.ts:171`) and the DB backstop is a RESTRICTIVE SELECT policy on `platform_metrics_weekly`, because a server action or `app/api/*` route sits outside `(admin)/layout.tsx` and page gating is not a gate. The policy predicate is a new `public.user_is_org_admin()`: `STABLE SECURITY DEFINER`, `SET search_path`, `SET row_security TO 'off'`, reading `public.user_organisations.role IN ('owner','admin')` for `auth.uid()` and never `current_user`, with the result `COALESCE`d to FALSE because a non-member yields NULL and `NULL IN (…)` is NULL. `OWNER_ADMIN` is a TypeScript constant (`packages/shared/src/types/index.ts:36`) and has no meaning inside Postgres; this function is its SQL counterpart. **`/metrics`, `public.user_is_org_admin()` and `public.touch_presence()` land with `docs/rbac-matrix.md` and `CONFORMANCE.md` updated in the same PR.** Both functions take `REVOKE ALL … FROM PUBLIC` plus an explicit `REVOKE … FROM anon`, verified with `has_function_privilege('anon', oid, 'EXECUTE')`, never by reading `proacl`.

**This table is the single source of truth for every headline target, and it is the table both roadmap halves now cite.** §13's and §14's exit-criteria tables each carry the header line *"Targets are §15 §(a)'s; this table restates them and does not set them"*, and the six cells that used to carry a different number for the same metric — §13's Q1 weekly-active denominator and its Q2 contractor figure, §14's Q3 RFI median and its Q4 weekly-active, diary same-day and inbox figures — are rewritten to this table's values and denominators. Where a roadmap cell and this table ever disagree again, this table governs. What follows the table is the audit trail: the divergences that were definitional rather than numeric, which still carry information, and the amendments themselves, so the correction is legible rather than silent.

#### Working days — Appendix A(h) governs

Four of the eight metrics, the chase ladder and the backfill's due-date floor all say "working days", and South African public holidays are not derivable from a date. **The calendar is defined once, in Appendix A(h), and this section reads it rather than restating it.** Four properties are repeated here only because metric 4 and the escalation rules stand on them:

- `projects.public_holidays(d date PRIMARY KEY, name text)` and `projects.calendar_years(year int PRIMARY KEY, seeded_at timestamptz)` are kept — but as a **materialisation, not a second source**. They are **seeded from the existing computus function** `listHolidays(year)` (`packages/shared/src/lib/jbcc/sa-public-holidays.ts:43`), with a contract test asserting the table equals `listHolidays()` for every seeded year. §13's `public.sa_public_holidays` is deleted.
- **The `works_saturdays boolean` this section previously proposed is deleted.** `projects.project_settings.working_days int[] NOT NULL DEFAULT ARRAY[1,2,3,4,5]` already exists (`00101_project_settings.sql:20`, verified, beside `extra_holidays`, `builders_holiday` and `holiday_calendar`) and already carries the working week; it simply drives no computation today, which is the real gap. A second column for a fact the first already holds is a drift waiting to be filed as a bug. **`office`** = `working_days` as stored, minus `public_holidays` and `extra_holidays`. **`site`** = `office` plus Saturday where Saturday is absent from `working_days` — SA sites work Saturdays, which is also why the recap fires `0 5 * * 1-6`.
- `projects.working_days_between(p_from, p_to, p_project, p_calendar)` is **`STABLE`, never `IMMUTABLE`** — it reads a table, and marking it immutable would let the planner fold a result across a calendar refresh. Both bounds are evaluated `AT TIME ZONE 'Africa/Johannesburg'`. A year with no `calendar_years` row raises `no_data_found`; **there is no fallback to calendar days**, because a silent one-day drift changes whether an item escalates. The October re-seed is a scheduled job in §(b2).
- **The statutory / operational split is absolute.** The JBCC time-bar engine keeps a fixed statutory South African calendar — Mon–Fri minus SA public holidays — and **never reads `project_settings`**, because JBCC defines "working day" in the contract, not in a project preference. A test asserts a JBCC deadline is byte-identical after `working_days` is edited. Metric 4 uses **office**; the chase ladder uses **site**; JBCC uses **statutory only**.

#### Fixture exclusion, stated as SQL

Every denominator excludes `rbac-test@e-site.live` — documented in `CLAUDE.md` as a permanent production regression fixture, not a user — and any account with `email LIKE '%probe%'`, the throwaway-admin pattern used for prod verification in PRs #142, #154, #158 and #162. The rule lives in one view, `public.metric_accounts`, and every metric query selects from it. A metric that quietly counts its own test fixture is the "fixture structurally incapable of failing" pattern in a new place.

#### (b2) Operating the scheduled estate

The programme's own history is the argument for this subsection: `cloud-sync-poll` was specified, merged and **never scheduled**, and all eleven of its runs to that point were manual — discovered only when users reported stale floor plans two months later. A scheduled job that stops running is silent by construction, and the twelve months add nine of them.

**Rule 1 — every job writes a run row on every tick, including a tick on which it did nothing.** A skipped run writes `status='skipped'` with the reason. "No row" must mean "did not run", never "ran and had nothing to do", because those two are the whole diagnostic.

**Rule 2 — a missing row inside the staleness threshold raises an Immediate-tier `job_missed` notification to the org owner** (registered Q1, Appendix A(c), `always_fires = true`, exempt from quiet hours and mute). The watchdog is one `pg_cron` job reading the ledgers, and it watches itself by writing its own run row.

### (c) Rollout and change management

**Pilot: KINGSWALK, from the first week of the Q1 release.** It is the only project dense across every living module — 102 floor plans, 131 boards, a live cable schedule, a maintained tenant schedule, QC entries and real RFIs — so the primitives are exercised against real content rather than seeded demo rows. **Snags exist only on a demo project and have never carried a single photo**; that module moves to KINGSWALK or it stays dead. **The one live site form is not a demo record**: `TMS-PNP2-2026-0001` was created through the UI on (649) PNP FAERIE GLEN on 12 August 2026 via the free-text board fallback (`CLAUDE.md`, 2026-08-12 entry) and is the forms module's only end-to-end reachability evidence. **Decision: snags move to KINGSWALK; the forms module is exercised on KINGSWALK in parallel, and the PNP record stays where it is** — it is evidence, and moving it destroys the only proof the creation flow works from the empty state.

**The conclusion, stated rather than implied: this programme is not revenue-funded, and it must not be sold internally as though it were.** It is WM's own build, paid for by WM, and **inside the window it returns 14.8–19.8% of its cost in internal saving** — the reporting-time line alone — with the rest carried as investment. The **18–23%** figure is the *first full year after the monday.com seats are cancelled*, not the programme window, and quoting it as the in-window return would be counting a saving the table itself records as R0 until Q4 ends. The revenue case is an **option**, not a plan: opened in Q3 with one signed letter of intent, tested in Q4 with two paying organisations, and worth pursuing only if both land. Thirty-two Practice organisations is the break-even a *product company* would have to reach, and nothing in this document claims WM reaches it in twelve months — saying so plainly is what keeps metric 8 an honest number instead of a target quietly redefined in month ten. If the option is to be taken, **question 10 has to be answered before the Q4 pricing cutover**, because the four bands go live in Q4 either way and a price list with nobody behind it converts nothing.
