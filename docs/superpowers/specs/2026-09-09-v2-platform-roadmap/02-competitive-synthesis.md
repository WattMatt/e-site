## What the best products do, and where E-Site can win

Six field products, five enterprise platforms, six work-OS tools, a dozen trade and certification apps and the AI frontier were reviewed. They disagree about almost everything except the shape of the daily habit. That shape is reproducible, cheap relative to what E-Site has already built, and — this is the section's central finding — **already half-paid-for**. A disproportionate share of the mechanics below land on machinery that exists in the repository, is fetched at runtime, and is then discarded one line before it would have changed behaviour.

### The patterns the winners share

**1. A single derived ball-in-court, never null, always dated.** Procore computes ball-in-court from workflow state — assignees while responses are outstanding, back to the RFI Manager when they land, to a forwardee on forward — and emails the new holder even when every other notification is muted. Autodesk Build shows *Ball in court* beside *Pending action from*; Aconex defines it at organisation level and lets an administrator make "response required" mandatory per mail type, so a due date always exists. Asana published the rationale for one assignee ("with two assignees one person may think the other has the ball") and Linear enforces it. E-Site's failure here is subtler than it looks. A project-default assignee mechanism already runs on every create path — `packages/shared/src/services/rfi.service.ts:79-82` resolves `input.assignedTo` and falls back to `projectSettings.defaultRfiAssigneeId` — and `apps/web/src/actions/rfi.actions.ts:70` even records which branch fired (`assigneeSource: 'explicit' | 'project_default' | 'none'`) as a deliberate post-deploy diagnostic. Fifteen production RFIs with a null `assigned_to` therefore prove that the fallback resolved to `none` every time, because **no project has ever had `default_rfi_assignee_id` populated** — the schema default is `null` (`packages/shared/src/schemas/project-settings.schema.ts:100`). An opt-in default is not a default. *What changes:* the assignee becomes structurally required at creation (Aconex's mandatory response-required), and a default assignee is seeded at project creation from the project's WM lead so the fallback is a real fallback. *What stays:* the resolution order, the diagnostic — which already exists to measure whether the fix worked. *Cost:* two schema edits, one project-creation write, no migration.

**2. The front door is a personal inbox that can reach zero.** Basecamp's *Hey!* carries only what is aimed at you — @mentions, to-dos assigned to you, completions of work you assigned. Linear's Inbox holds only subscribed issues and, since September 2026, splits Priority from the rest. Procore's My Open Items, Autodesk's "Assigned to Me" card and Aconex's Tasks page are the same organ at enterprise scale. E-Site's equivalent is a bell dropdown that cannot become an inbox by extension. It fetches with a hard `.limit(30)` and no paging (`apps/web/src/components/ui/NotificationCentre.tsx:41-46`), so against 964 notifications a user cannot see their own backlog; its only bulk action is an unscoped `update({ is_read: true }).eq('is_read', false)` across every notification the user can write (`:49-58`), so the single affordance for a full bell is to erase it; and `markRead` fires on click-through (`:60-63`), which is why 57 of 964 are read. It must be replaced, not upgraded. The queries that would populate a real inbox already exist and are three signature changes away: `getAwaitingVerification`, `getReInspectRequired` and `getStaleDraftInspections` each take `orgIds: string[]` and filter `.in('organisation_id', orgIds)` with no user predicate (`packages/shared/src/services/sla.service.ts:139-190`), and `getSlaSummary` is org-scoped in the same way (`:256`). *Cost:* a user predicate on five queries plus a new route; the retrieval logic is written.

**3. Notify by exception, batch by default, suppress when present.** Fieldwire coalesces task changes for five minutes and caps them at one email per record per hour, excluding the author. Linear sends email only if the in-app notification is still unread and delays it by urgency. Basecamp does not email you if you are active in Basecamp; Notion shows a badge only while the tab is open; Slack's push waits for desktop inactivity. E-Site's RFI creation fans a bell notification to every project member except the raiser, unconditionally (`apps/web/src/actions/rfi.actions.ts:84-95`) — which is how 964 notifications produced 57 reads and 750 of them were `diary_created`. Copy urgency-keyed delivery with three user-level settings, not forty checkboxes. *What stays:* `dispatchNotification` and the recipient resolver; the batching, presence gate and urgency key wrap them. The type vocabulary and the tier each type is delivered at are Appendix A(c)'s, not this section's.

**4. Email is a participation channel, not a pointer.** Procore mints a reply-to address bound to each RFI and posts the reply, with attachments, onto the record; Autodesk does the same for the ball-in-court holder; Asana treats `To:` as reassignment and `CC:` as add-follower; Basecamp calls it "adoptional" — anyone can take part without doing anything but replying to an occasional email. E-Site's emails are one-way links ("View RFI", `packages/shared/src/email/rfi-email.ts:81`) and the repository contains **no inbound-mail handling of any kind**: a search for `inbound`, `reply-to` and `replyTo` across `apps/web/src`, `packages/shared/src` and `apps/edge-functions/supabase/functions` returns zero matches. Given 13 contractor accounts with zero sign-ins in 30 days, reply-by-email is not a convenience, it is the participation model — which makes it the one proposal in this section that must arrive with an authentication design, not after one. **The reply address carries an opaque per-recipient, per-item HMAC token** — §05 owns its shape, `wi-<short_id>-<hmac10>@in.e-site.live` — the inbound webhook verifies the mail provider's signature, resolves the token to a `(user_id, item_id)` pair, and **ignores the `From:` header entirely**; a `From:` header is not an authentication factor and an unresolvable or expired token bounces rather than posting. `To:` and `CC:` semantics act only within the permissions the token's user already holds, resolved through `user_effective_project_role` (`apps/web/src/lib/auth/require-role.ts:94`), so a mail header can never grant access its sender lacks. Gated in the app and in the DB, per the standing rule that page-level gating is not a gate.

**5. Capture removes decisions, not just keystrokes.** CompanyCam files a photo to the project by GPS with no prompt; Raken stamps weather automatically and takes voice-to-text; Dalux opens a location's issues, checklists and inspections from a printed QR; OpenSpace Field fills form fields from speech and locates the user indoors without hardware, which Suffolk measured at 86% faster issue documentation. The trade tools are sharper still: Elec-Mate photographs a distribution board and populates the circuit schedule, iCertifi reads results off the meter display, and ECA(SA)'s eCoC claims "around 40% of the work is already done" by prefill. E-Site types its own weather into a free-text field (`packages/shared/src/schemas/diary.schema.ts:28` — `weather: z.string().max(100).optional()`). **The entry date, however, is already auto-defaulted on both capture surfaces** — `apps/web/src/app/(admin)/projects/[id]/diary/AddDiaryEntryForm.tsx:33` and `apps/mobile/app/diary/[projectId].tsx:29` both initialise state to `new Date().toISOString().slice(0, 10)` — and the two-day median lag between `entry_date` and `created_at` persists anyway, because the contractor is not in the app on the day and back-dates when he returns. That is the most useful lesson available to the whole capture layer: **auto-filling a field is necessary and not sufficient; the record is late because nothing asks for it on the day.** The fix is a recurring check-in at a set time and a one-tap "no work today" (mechanics rows 13 and 14), not a better date picker.

**6. The deliverable is a branded PDF nobody had to write, and it can be scheduled.** Every field product ships a logo-bearing, filterable PDF that emails to non-users; Fieldwire and Procore schedule it; Raken's Super Daily merges every subcontractor's daily into the consultant's one document; Buildertrend drafts the weekly client update from logs, schedule and change orders and reports ~6.5 minutes per update. E-Site's report engine is genuinely good and genuinely finished: one unified table carrying `kind`, `version`, `superseded_by` and `generated_by` (`apps/edge-functions/supabase/migrations/00117_report_export_branding.sql:44-63`), with list, signed-URL and delete actions over it (`apps/web/src/actions/project-reports.actions.ts:29-30`, `:59-80`). What it has no concept of is a schedule — the word does not appear in that file. The instructive number is not the total of nine saved reports (two of the three kinds are weeks old at the measurement date) but the **seven tenant-schedule reports**: that renderer sits on the most-used module in the product, 265 rows created in the last 30 days across 14 projects, and has produced seven documents in its life, because every one required a person to decide to press a button. *Cost:* a scheduler row per project and a cron tick; the renderers and the version chain exist. Which report kinds exist, and who may read each, is Appendix A(d)'s registry.

**7. Compliance is enforced by a workflow gate, not a reminder.** Simpro shows outstanding mandatory asset readings in red until they are cleared; ServiceM8 makes a form a mandatory checklist item at job start or end; Aconex makes response-required mandatory at the mail-type level. E-Site has already proved this works and proved it server-side: `evaluateSubmitGates` (`packages/shared/src/site-forms/gates.ts:169`) is called from the submit action itself (`apps/web/src/actions/site-forms.actions.ts:553`) alongside a required-field completeness check, with a comment recording that three taps previously produced a `submitted` record that read as complete to the list, the PDF and the email. Extend the pattern to energising, handover and practical completion rather than adding notifications. *Cost:* the gate evaluator is generic over responses; each new gate is a rule, not a subsystem.

**8. Free for the people who did not buy it.** PlanRadar charges for in-house users and gives unlimited subcontractors and watchers; Dalux Field Basic is free with unlimited users; Raken's collaborators submit dailies free; Novade's View-Only role is free on every plan; Procore, Aconex and ProjectSight Free are unlimited-user by design. Autodesk's per-user, per-module licensing is the outlier and is the top complaint in its review set. E-Site advertises 5 / 10 / 30 users by tier (`packages/shared/src/services/billing.service.ts:23`, `:33`, `:43`) — and **never enforces them**: `limits.users` is read nowhere in the monorepo, and the only limit ever checked is `limits.projects`, at `apps/web/src/actions/project.actions.ts:68`. The honest version is worse than the overstated one. The caps deter exactly the external participation the product depends on, in front of every prospect who reads the pricing page, and collect nothing for it.

**9. Role narrows the interface; the phone gets one job.** PlanRadar's subcontractor can only update tickets assigned to them; Dalux scopes task visibility to teams so the supply chain is not drowned; Linear's mobile app is Inbox, My Issues and capture, and took four years to gain document editing because parity was never the goal. E-Site offers the same sixteen project entries to every role (`apps/web/src/components/layout/Sidebar.tsx:73-88`), **filtered only by paywall visibility, never by role**: the sole project-nav filter is `mvVisible` (`:155-156`) and JBCC and Medium Voltage render a `LockedBadge` rather than disappearing (`:173-174`). The `role` prop narrows only the global nav and the footer (`:123-129`). *What changes:* role narrows the project nav to the modules that role can act in, and the first two entries for every role are the personal surfaces — Inbox and My Work, `/inbox` and `/my-work` in Appendix A(g)'s new `(work)` group — which today have no route at all (no `inbox`, `my-work` or `today` directory exists under `apps/web/src/app`).

**10. Onboarding is the product doing its job, measured in the first session.** Linear's onboarding checklist is itself a set of issues in the new workspace and activation is the first issue completed; Notion's is a live page. With 5 accounts that have never signed in and 6 projects holding a single member and nothing else, the fix is not a tour — it is five real work items waiting for the new user, and an activation metric that reads "first work item closed in session one".

Rows 13, 15, 16 and 17 land in Q2, Q3, Q4 and Q4 respectively; row 12, **row 23** and the offline write queue named under "Lossy offline sync" below are not built inside the programme and are retained only as designs. Row 12 and the write queue are schedule cuts and could return in a later window; **row 23 is not a schedule cut at all** — §11.4's read-only-by-construction ruling forecloses it, and no quarter's spare capacity would reverse that.

**Row 1 in detail, because it is the primitive everything else hangs off.** The holder is a `STORED` generated column on `projects.work_items`: `ball_in_court_id`, a `CASE` over `status` that selects `assignee_id` while the item is `triage` or `open`, `gatekeeper_id` once it is `answered`, and null only at `closed` and `void`. Three columns of the same row, no subquery and no function call — legal Postgres, and §03 governs it; the authoritative DDL is Appendix A(a). The value cannot drift out of step with the status it is derived from, cannot be forged by a direct PostgREST write, and needs no recompute path at all.

**`work_items_bic_present` is what makes "never null while open" a database fact rather than an intention** — `CHECK (status IN ('closed','void') OR ball_in_court_id IS NOT NULL)`, protecting the property against a later edit of the expression as much as against bad data. Everything the outside world knows about the ball arrives through `status`, which the **per-source mirror triggers** write: a row landing in `projects.rfi_responses`, a form's submit gate clearing, `node_orders.status` reaching `ordered`, a snag reaching `resolved`. The triggers own the transition; the generated column owns the person. Procore's manual shift therefore writes whichever person column the current status selects — `assignee_id` while `triage` or `open`, `gatekeeper_id` at `answered` — which §03 §1.4 ships as one server action with a `BEFORE UPDATE` guard rejecting a write to the column the current status does not select.

**The objection this section originally raised is correct, and its scope is worth stating rather than quietly dropping.** A generated column must be immutable and may reference only columns of its own row: it cannot read a child table and it cannot call `now()`. So a ball-in-court derived the obvious way — for an RFI from whether an outstanding `projects.rfi_responses` row exists, for a site form from `field.form_signatures`, for an inspection from `inspections.responses`, with overdue escalation read off the clock — genuinely cannot be a generated column, and written as one the migration will not apply. That design needs trigger-maintained columns and a recompute function fired from every child table that can shift the ball. **The programme does not build that design, so the objection does not bite.** Child-table facts and the clock enter through the mirror trigger, which writes a plain `status` column; the generated expression then picks a person out of the same row. The reasoning stands against the design that was rejected, not against the one that ships.

Two standing constraints still bind the mirror and write-back triggers, because they are `SECURITY DEFINER`: the functions must never use `current_user` for an authorisation decision, since it resolves to the function owner — the defect that made the site-forms transition trigger inert on first ship — and each needs `REVOKE … FROM PUBLIC` plus an explicit `anon` revoke, verified with `has_function_privilege`. After the migration, read the affected table back: a green deploy is not evidence a migration ran.

**Which sources are registered, and when, is Appendix A(b) — not a list this section maintains.** The eventual registry ambition is that every module with a lifecycle mirrors into the spine; the committed reality is narrower. RFIs, snags, QC defects, diary actions, form actions, order follow-ups and **inspections** register in **Q1**; instructions arrive in Q2, approvals in Q3, valuations in Q4. **JBCC letters are not registered at all** — JBCC keeps its own time-bar engine on its own statutory calendar (Position 2 below, and Appendix A(h)), and folding it into the spine would put a contractual deadline at the mercy of a project preference.

### What the incumbents get wrong — and what that gives us

**Opaque pricing and renewal shocks.** Raken and Buildertrend are demo-gated, and Buildertrend's 50–75% renewal hikes dominate its review set; PlanRadar has a documented $2,000 auto-renewal trap; monday.com averages 2.7 on Trustpilot across 3,300+ reviews with billing in nearly every negative one; Procore's own sales tells ten-person firms they are too small. **Opportunity:** publish ZAR list pricing with no minimum seats and no renewal escalator, and say so on the pricing page. Every competitor's worst review is a billing surprise.

**Per-seat licensing that taxes participation.** Autodesk charges $35–85 per user per month per module; CompanyCam bills phantom seats on a three-user minimum; monday.com sells seats in blocks of 3/5/10/15/20 so a team of six pays for ten. The workflow needs exactly the people the licence punishes. **Opportunity:** price the network rather than the seat. The billing unit — per project or per consultancy — is settled in the pricing section, not here; the invariant this section owns is that **no external party is ever a billable seat**: contractors, clients, other consultants and account-free guests participate at zero marginal cost, on every tier, permanently. The immediate change is to delete the 5 / 10 / 30 user counts from `PLANS` (`billing.service.ts:23`, `:33`, `:43`) and from the pricing copy. That is a constants-and-copy edit; there is no gate to unwind, because the cap was never enforced.

**Notification floods with no inbox.** The top-voted Autodesk idea asks for in-app notifications "instead of multiple emails"; an Asana user reports four emails for one event; a monday.com consultant writes that people stop paying attention. Digests are a workaround for a missing inbox. **Opportunity:** ship the inbox first and the digest second — E-Site's 57-of-964 read rate is the same disease at a smaller scale, and its bell has no paging and one bulk verb.

**Configuration-heavy workflows nobody sets up.** Aconex mail-type rules, Autodesk review templates, Procore permission templates and monday automations all assume an administrator who will never exist in a firm this size. E-Site has already reproduced the failure at small scale: `default_rfi_assignee_id` is a perfectly good routing mechanism that no project has ever configured. **Opportunity:** opinionated defaults seeded at project creation, at most two notification scopes, and item types shipped pre-wired for an electrical consultancy. A setting that must be turned on is a setting that does not exist.

**Lossy offline sync.** Dalux reviewers report reports lost out of range; Novade Lite photos that will not save; Raken's Android app sits a full star below iOS across ~2,400 reviews; Tradify and ElectraForm have no offline mode at all and are punished for it. **Opportunity:** orphan-safe uploads with a visible sync chip — E-Site already learned the orphan-safe upload lesson in the snag module — and Android-equal behaviour. This is the most expensive opportunity in the list: `apps/web` contains no manifest, no service worker and no reference to `serviceWorker`, `next-pwa` or `workbox`, so the PWA shell is genuinely net-new work, not a configuration flag. The shell and web push ship in Q2; the **offline write queue is cut past twelve months**, so the honest Q2 promise is an installable app with a sync chip, not one that accepts writes out of range.

### The white space E-Site can own

These three positions rest on Forms, JBCC and Tenant Schedule — two of which the declutter decision turns off by default. That is not a contradiction, because **off-by-default is a first-run decision, not a strategic one**: the toggles exist so a new, empty project shows only the modules every project uses, and Positions 1 and 2 are precisely the modules a project turns on the moment it has a CoC obligation or a JBCC contract. **The default set is Appendix A(e)'s and is not restated here** — Tenant Schedule, Cables, Quality Control, Inspections and Equipment & Materials on; Forms, JBCC, Handover, Medium Voltage and Generator Cost Recovery off. What this section owns is when a project is *prompted* to turn the last two on, because a toggle nobody is offered is a toggle nobody uses: **Forms is offered the moment the submit gates detect energising**, which they already compute; and **the JBCC toggle is offered at project creation whenever `contractType` is `'jbcc_pba'`**, which is the value every new project already gets (`project-settings.schema.ts:103`). A South African building contract is the norm, not the exception, and a prompt that ignores a setting the product already stores is a prompt that will never fire.

**Position 1 — the CoC that is linked to the installation data, not a standalone form.** ECA(SA)'s eCoC is the only SA-native digital CoC and it is a form filler; it prefills from membership records, not from the installation. Nothing in the SA market does meter OCR, board scanning, or links a certificate to the DB register and cable schedule that it certifies; ECA(SA)'s own "essential apps" list contains calculators and vendor configurators, no workflow tools. E-Site already reads the other side of that link. A new site form is populated from the project record, the board node and the cable schedule, with the sources chosen by measuring what is actually populated in production rather than by reading the schema — the file records that `structure.node_circuits` is effectively empty and `tenant_details.db_fed_from` is null in all 411 rows, while the cable schedule holds 374 supplies across 6 of 14 projects (`apps/web/src/lib/site-forms/prefill-sources.ts:10-19`, `:135-183`), and inspections already allocate a CoC number through `allocate_coc_number` (`apps/web/src/actions/inspections-certify.actions.ts:220`). ECA(SA) also publishes the fraud problem: certificates bought against a contractor's registration, admin staff holding the registered person's password and signature image. Device-bound signing by the registered person, an immutable lock and a full audit of who certified what is a defensible product, not a feature. *Cost:* the prefill chain and the number allocator exist and are already live, so the cheap half of this position is banked. The expensive half — device-bound signing, the immutable lock and the audit surface — is **cut past twelve months** in the Q3 re-plan and retained as a design in §14, on that section's own reasoning that the costly part is getting registered persons onto accounts at all, which the programme is only now achieving.

**Position 2 — JBCC-compliant instructions and an electronically submitted site diary.** JBCC Advisory Note 17 requires an instruction to be in writing, properly identified and dated, with receipt signed by the contractor, and states explicitly that a site-instruction-book entry is not good practice. The Principal Building Agreement requires the contractor to maintain daily records of persons and plant; the evidence standard for an extension-of-time claim is a site diary signed off by an independent party or submitted electronically. No dedicated JBCC administration software exists in South Africa — the market is Word template packs and document portals. E-Site is most of the way there: notice letters carry a controlled ISO lifecycle (`submit_for_review → approve → issue → mark_served` with service method and reference, `packages/shared/src/schemas/jbcc.schema.ts:56-67`), and time-bar deadlines are computed by `computeDeadline`, which handles **both working days and calendar days** (`packages/shared/src/lib/jbcc/working-days.ts:37-41`) against the fixed statutory calendar Appendix A(h) preserves for it. Two gaps close the position, and the first needs a rule stated before it is built, because deemed receipt is already seeded: PBA 2.5 / MWA 2.5, "email = 1 WD; registered post = 7 CD" (`apps/edge-functions/supabase/migrations/00099_jbcc_module.sql:340`). **Decision: the deadline clock always runs from deemed receipt per the seeded time-bar schedule. An actual acknowledgement is recorded alongside it as corroborating evidence and never moves the deadline, earlier or later** — a contractual record exists to remove ambiguity, and two competing start dates would manufacture it. Concretely, `acknowledged_at` and `acknowledged_by` join `served_date` and `service_method` on `projects.jbcc_letters` (which today has neither, `00099:103-122`), and the acknowledgement arrives through the same signed-token email path as mechanics row 11, so a recipient with no account can still produce one. The second gap is the diary: `projects.site_diary_entries` has no submitted, signed or countersigned column at all (`apps/edge-functions/supabase/migrations/00002_projects_schema.sql:146-158`), and a repo-wide search for `countersign` and `acknowledg` returns hits only inside the site-forms template JSON — the concept exists in the product and has never reached the diary. A submit state, a daily labour and plant count, and an optional principal-agent countersign turn a records module into contractual evidence. *Cost and schedule:* **both changes are booked as §13's Q2 item 13, "Diary countersign and JBCC acknowledgement", at 0.5 engineer-weeks in total** — Arno's lane, starting after the diary check-in (Q2 item 12), in the same quarter as the instruction register rather than beside it on the chain — one migration across the two tables, and **the deemed-receipt rule ships in that same migration** so the clock and the acknowledgement column arrive together and no letter is ever written under the old ambiguity. That half-week is the only engineer-week figure this section states, and §13's Q2 ledger now carries it; §06's separate 0.5 for the recipient-scoped branch in `user_can_read_report_kind()` is a distinct line, which §13 books on its own as **Q2 item 15** rather than folding it into the instruction register, so neither half-week absorbs the other. The token path is already required by row 11.

**Position 3 — tenant coordination that carries electrical data.** SA landlords run tenant installations on spreadsheets and hire PM firms for coordination; TCTrac and the lease-management suites track dates and costs, and none of them carry electrical data. The CoC is part of the paperwork behind an occupation certificate, so the landlord's delivery milestone and the electrical record are the same object viewed twice. E-Site's tenant schedule is its most-used module — 265 rows created in the last 30 days, and 7 of the 9 saved reports in the whole system — and already links tenant to board to scope items to documents. A tenant-delivery tracker (lease → drawings approved → beneficial occupation → CoC → occupation certificate) with a landlord-facing read-only view is the only product in the SA market that would connect the two, and it lands on data E-Site already maintains for its own reasons. *Cost:* a status ladder over existing rows and one client surface — the cheapest of the three positions and the one with a live audience, since client viewers last signed in on 8 July 2026 and have had nothing to come back for.

### What we are choosing not to copy

| Not copying | Exemplar | Why |
|---|---|---|
| Computer-vision progress tracking against BIM | Buildots, DroneDeploy Progress AI | Requires a model, a maintained schedule, 360 hardware and disciplined walks; no SA retail fit-out has those inputs, and OpenSpace pays human verifiers for its own output |
| 360 reality capture as a platform | OpenSpace, DroneDeploy | Commodity and hardware-bound; link out if a client asks |
| Predictive schedule risk from historical projects | Slate.ai | Needs hundreds of completed projects; E-Site has 14, of which 5 hold real data |
| Per-seat, per-module licensing | Autodesk Construction Cloud | Directly taxes the contractors and clients whose participation is the product's whole problem |
| Per-certificate pricing | ElectraForm £1, NICEIC £1.55 | The most-cited churn reason in the UK certification market; flat and unlimited wins under ~50 field staff |
| App-store publication this version | Fieldwire, PlanRadar, Dalux | Zero production push tokens and zero installs say the store is not the constraint; a web-first PWA with web push carries the same jobs |
| Mobile feature parity with the web | Novade, Raken | Linear shipped mobile document editing four years late on purpose; the phone gets capture and inbox, nothing else |
| Multi-assignee work items | Basecamp to-dos, monday People column | Asana's published reasoning is correct, and `work_items_bic_present` — a `CHECK` that ball-in-court is never null while open — is impossible to hold with two owners |
| Configuration-heavy workflow builders | Aconex mail types, ACC review templates, monday automations | A one-PM consultancy will never configure them, so the good defaults never exist — `default_rfi_assignee_id` is the in-house proof |
| Per-notification-type toggle sprawl | Asana, monday | Users do not tune forty checkboxes; group the types and offer two or three scopes |
| Silent staleness expiry | monday My Work drops items untouched for four months | Hides stale work; escalate to the assigner instead |
| Sender-authenticated inbound mail | Most reply-by-email implementations | A `From:` header is trivially spoofable and `To:`-reassignment is a privilege-granting operation; the token authenticates, the headers never do |
| Marketplace, FSM and estimating expansion | CompanyCam bloat, Novade | Reviewers are already paying for modules they ignore; E-Site's own marketplace has 2 orders, both from April |
| Autonomous agents that act without review | Procore Agent Builder, Trunk RFI agents | Anything feeding a CoC or a JBCC notice must be human-signed; drafts yes, decisions no |
| Document-RAG question answering as the first AI surface | Trunk Tools | 87% accuracy is honest, but structured queries over the cable schedule and order ledger are more accurate and cheaper; do that first |
