## Access model, external participation and pricing

Thirteen contractor accounts exist and none has signed in for thirty days; four never have. That is not a permissions failure — they already hold `contractor`, the broadest non-admin role we grant (`packages/shared/src/types/index.ts:54`, `:92`). It is a participation failure: E-Site asks an external party to create a password, learn a shell and remember a URL before it gives them anything. The field-first cohort solved this by making the people who did not buy the software free and low-ceremony (`research/01-field-first.md:41,79,98,117`); Procore and Aconex charge the organisation and never the participant (`research/02-enterprise.md:17,55`). This section does the same, using the role strings we already have.

Every claim below about live state was measured against the production database on 2026-09-09 via the Management API query endpoint, and is quoted with its figure. Where this section touches a registry, a table inventory, a route list or a vendor, **Appendix A is the source of truth and is cited rather than copied**.

### 11.1 The revised role model

Seven org roles are declared in `ORG_ROLES` (`packages/shared/src/types/index.ts:7–15`) and permuted across nine role-group constants (`:36–94`), each documented as "distinct even though the sets coincide today". What is missing is not vocabulary but a stated *capability* boundary — one answer to "who may commit the organisation".

| Tier | Existing role strings | Ceiling |
|---|---|---|
| **Paying core** | `owner`, `admin`, `project_manager` — exactly `ORG_WRITE_ROLES` (`types/index.ts:37`) | Everything: cost, billing, membership, module toggles, project creation |
| **Update-only participant** | `contractor`, `inspector` (org role, or `projects.project_members.role`) | Create/close work items, capture, comment, submit forms; never cost, never membership, never module settings |
| **Watcher** | `client_viewer` | **The client-viewer write set, by quarter. This row is the single statement of it; every other section cites this row and none restates it.** · **Q1 — no project write of any kind.** Snooze and clear act on the watcher's *own* `public.inbox_state` row and on nothing else (§04's own-row policy); they change no project record. · **Q2 — thread messages**, subject to `projects.project_settings.client_comments_enabled` (Appendix A(f) Q1 column adds; §06 §4.1), enforced by a RESTRICTIVE INSERT policy that tests the role predicate **and** the setting; **and acknowledgement of an instruction addressed to them**, which writes their own `projects.instruction_recipients` row and nothing else — never on another party's behalf, because the token is minted per recipient row and the row *is* the gate (§06 §4.5). · **Q3 — approval decisions on the §14 Q3.7 list**: documents and drawings, milestone and beneficial-occupation acceptance, and issued reports — **variations are deliberately excluded**, because `COST_VIEW_ROLES` excludes `client_viewer` (`types/index.ts:61`) so a watcher cannot see a variation's value and approving one blind is commercially meaningless; **and `triage\|open → answered` on a work item they are the assignee of**, so an item pointed at the landlord can leave their inbox. · **Nothing else, in any quarter**: never cost, never membership, never module settings, never authoring an instruction, a minute, a transmittal or a report. |
| **Guest** | no account, no row in `auth.users` | One scoped link, one purpose, expiring (§11.4) |
| **Out of the project model** | `supplier` | Marketplace only — and Marketplace is **not** a per-project toggle: it is org-level and removed from navigation entirely (Appendix A(e); §11.7) |

The watcher row is deliberately a *ratchet*, not a single grant: each quarter's addition is the smallest write that makes that quarter's deliverable usable, and it is scoped by **row** rather than by role. A blanket block would be worse than useless — in a shopping-centre fit-out the landlord frequently *is* the ball-in-court, and `work_items_bic_present` (Appendix A(a)) guarantees an item keeps pointing at them, so a watcher who can never reach `answered` has an inbox that can never reach zero.

**Decision: `ORG_WRITE_ROLES` is the capability boundary — the set that may create projects, administer membership and change module settings — and it is not a billing meter.** Because §11.7 prices per organisation and bands on active projects, no role is counted for billing and nothing in the platform ever counts users. One constant, already the write gate on every commercial surface, is reused rather than a second one invented.

**Decision: no role string is retired and no membership row is rewritten.** The draft of this section proposed re-mapping `inspector` and `supplier` to `contractor`; that is a privilege escalation, not a simplification. `inspector` is strictly *narrower* than `contractor` on roughly twenty matrix rows and broader on exactly one:

| Matrix row | contractor | inspector | Effect of a naive re-map |
|---|---|---|---|
| `/projects` (list), `/projects/[id]` (overview) — `rbac-matrix.md:40–41` | W | R | read → write on the project record |
| `/projects/[id]/diary` — `:47` | W | R | gains diary authoring |
| `/projects/[id]/quality-control` ×3 — `:44–46` | W | R | gains QC report authoring |
| `/projects/[id]/floor-plans`, `/rfis` — `:57`, `:60` | W | R | gains markup + RFI authoring |
| `/projects/[id]/tenant-schedule`, `/equipment-materials` — `:53`, `:56` | W | — | denied → full write |
| `/projects/[id]/jbcc/*` ×6 and `GET /api/jbcc/sign` — `:74–79`, `:195` | W⁵ | — | denied → authoring **and signing** contractual notices |
| `/projects/[id]/inspections` — `:59` | R² | W² | the one row where inspector is broader; a re-map would *remove* the inspector's only distinct capability |

`supplier` is narrower still: `—` on `/projects` (list) itself (`rbac-matrix.md:40`) and on every project route except `/marketplace/supplier/*` (`:64`). Re-mapping it to `contractor` would take an account with no project visibility at all and hand it write access to fourteen projects.

The re-map is refused, and it is also unnecessary: **production holds zero rows carrying either string.** `public.user_organisations` is `admin` 14 (12 active), `contractor` 13 (all active), `client_viewer` 4, `owner` 2 — and nothing else. `projects.project_members` is `project_manager` 22, `contractor` 21, `client_viewer` 4. Both roles have existed since `00001` (April 2026) across 36 accounts and have never once been assigned; that is five months of non-adoption, not a young module. `inspector` therefore sits inside the update-only tier as a narrower contractor and is left alone; `supplier` sits outside the project access model and is parked with the marketplace.

⚠ **A consequence an implementer must not "tidy" away.** `SNAG_FIELD_ROLES` (`types/index.ts:54`) and `FORMS_FIELD_ROLES` (`:92–94`) are *derived* from `ORG_ROLES` by filter, not enumerated. Removing a string from `ORG_ROLES` silently removes it from both write sets; adding one silently adds it. Because we retire nothing, the sets are unchanged — but any future edit to `ORG_ROLES` must re-cut both constants explicitly in the same commit.

**Decision: narrow the `user_organisations` role CHECK back to the seven `ORG_ROLES` values.** The live constraint is not `00001_initial_schema.sql:102` — it was dropped and re-declared with **eleven** values at `00022_schema_patches.sql:38–44`, adding `field_worker`, `supervisor`, `viewer` and `member`, none of which appear in `ORG_ROLES`. A row carrying one of those four maps to no tier: `user_effective_project_role` clause 1 (`00107_user_effective_project_role.sql:59–61`) will not match it, and with no `project_members` row clause 3 returns NULL, so every `allowedRoles.includes(role)` gate in `require-role.ts` fails closed with an unhelpful error rather than a decision. This is not hypothetical — the mobile invite screen upserts the literal `'member'` (`docs/rbac-matrix.md:452`). **Production holds zero rows with any of the four**, so the narrowing migration re-maps nothing and is a pure constraint change; the same PR deletes the dead mobile upsert that `00177` already denies. Without the narrowing the tier model has an undefined region, which is exactly the kind of gap that becomes a billing or access dispute later.

`projects.project_members.role` is left as declared (`00002_projects_schema.sql:46`: five values, already a subset of `ORG_ROLES`).

**Decision: offboarding is a defined transaction, not a membership DELETE.** Because `work_items.assignee_id` and `gatekeeper_id` are both `NOT NULL` (Appendix A(a)) and `work_items_bic_present` forbids a live item with no holder, removing a person is a *data* event before it is an access event. On membership removal or profile deactivation, in one transaction:

1. **Every open work item** (`status IN ('triage','open','answered')`) where the leaver is `assignee_id` **or** `gatekeeper_id` is reassigned to the project's `triage_owner_id` (`projects.project_settings`, Appendix A(f) Q1 column adds), and **each reassignment writes a `work_item_events` row** naming the leaver, the new holder and `reason='participant_removed'`. Silent reassignment would make the audit trail claim the triage owner had always held the item.
2. **Every credential the leaver held or minted is revoked**: their reply-by-email tokens (§11.3 — the per-recipient HMAC is revocable precisely because it is per recipient), their ICS feed token (`profiles.ics_token_hash`, Appendix A(f) Q4), and **any `public.guest_links` row where they are `created_by`**, which is stamped `revoked_at = now()` rather than deleted so the redemption audit stays readable.
3. **An unfulfilled acknowledgement is never back-filled and never guessed.** An `instruction_recipients` row with no `acknowledged_at` prints on the instruction PDF, the register and the portal as **"not acknowledged — recipient no longer a project participant"**, never as acknowledged and never as a blank. This is the `as_left_status` lesson in a different table: the safest-sounding default is the most dangerous thing to invent, because nobody double-checks it.

The reassignment is a `SECURITY DEFINER` function taking the leaver's id explicitly and gated on `ORG_WRITE_ROLES`; it never reads `current_user`, and it is called by the same server action that removes the membership so the two cannot diverge.

### 11.2 Enforcing "free" in the database

Free participation is only credible if the ceiling is real. Page-level gating is not a gate: server actions and `app/api/*` sit outside `(admin)/layout.tsx`, and `requireRolePage` (`apps/web/src/lib/auth/require-role.ts:171–181`) only redirects a render. The pattern that works is already in the repo — a SECURITY DEFINER helper plus a RESTRICTIVE policy AND-combined over whatever permissive policies exist (`00177_membership_write_authz_rls.sql:281–315`, helpers at `:232`/`:256`).

| Gate | Mechanism | Applies to | Effect |
|---|---|---|---|
| Commercial read — tables | `public.user_can_view_cost(p_project_id)` → `user_effective_project_role` ∈ `COST_VIEW_ROLES` (`types/index.ts:61`) | `projects.boq_items`, `projects.valuations`, `projects.variation_orders`, `cable_schedule.rate_library` | RESTRICTIVE SELECT; a contractor or watcher reading PostgREST directly gets zero rows, not a redacted page |
| Commercial read — columns | `REVOKE SELECT (contract_value, currency) ON projects.projects FROM authenticated` plus a SECURITY DEFINER accessor gated on `user_can_view_cost()` | `projects.projects.contract_value`, `.currency`; `projects.project_settings.retention_pct` | Column privileges, **not** RLS |
| Module toggle write | `public.user_can_configure_project(p_project_id)` → `ORG_WRITE_ROLES` | `projects.project_settings`, including `enabled_modules` (Appendix A(e) owns the token set and the default-ON column default) | RESTRICTIVE INSERT/UPDATE |
| Membership write | already written | `projects.project_members`, `public.user_organisations` | `00177` (pending merge/apply per `CONFORMANCE.md:61`) — **apply it before Q1 ships**; without it a free participant can self-promote into the paying core |

⚠ **The commercial-read gate is deliberately split across two mechanisms because Postgres RLS has no column-level policies.** A RESTRICTIVE SELECT on `projects.projects` scoped to `COST_VIEW_ROLES` would hide the *entire project row* from every contractor and watcher, breaking `requirePortalAccess` and every project read in the app. Column privileges are the correct instrument; the app-side allow-list the portal already uses (`apps/web/src/lib/portal/data.ts:57–58`, where `contract_value` is deliberately absent) stays in place as the second gate rather than being replaced by it.

Four constraints govern every one of these functions and are non-negotiable. `REVOKE ALL … FROM PUBLIC` **and** an explicit revoke for `anon`, verified with `has_function_privilege('anon', oid, 'EXECUTE')` and never by reading `proacl` (the `00177` helpers do the first half at `:251`/`:273`; the anon half must be added). Never `current_user` inside a SECURITY DEFINER body — it resolves to the function owner. `COALESCE` the role comparison, because `user_effective_project_role` returns NULL for a non-member and `NULL IN (…)` is NULL. And resolve the client-viewer question through `user_effective_project_role` (`00107:30–68`), never `user_is_client_viewer`, for the reason `00181_client_viewer_project_aware_rls.sql:24–34` documents at length: the sanctioned external-client path (`project-members-from-sub-org.actions.ts:142–150`) inserts a member whose `organisation_id` is the **sub-org**, so the org-only predicate does not recognise them.

The client-viewer write policies these gates carry are exactly the §11.1 Watcher row's set, per quarter, and are not re-derived here.

### 11.3 Email-only participation

A contractor should be able to work a full week through their inbox and never see a login screen. Reply-by-email is a full participation channel, not a courtesy.

| Without an account | Requires sign-in |
|---|---|
| Reply to a work-item email → comment posted, attachments ingested | Signing a site form (`field.form_signatures`) |
| **Reply `done` → the item moves `open → answered`; closing remains the gatekeeper's** | Signing off a snag |
| Reply with photos → filed to the item as evidence | Issuing or voiding a distributed record |
| Receive the 07:00 recap and per-item mail | Any cost surface |
| Open a guest link (§11.4) | Changing membership or module settings |

**Decision: `done` never closes, because closing is the gatekeeper's and only the gatekeeper's** (§03 §1.8 — one gatekeeper per item, enforced by a `BEFORE UPDATE` trigger comparing `auth.uid()` to `NEW.gatekeeper_id`, never `current_user`). **The mail channel has exactly three verbs — a bare reply, `done` and `closed` — and only one of them can reach `closed`, only in the gatekeeper's hands.** A bare reply posts a comment and, from the assignee, moves `open → answered`. `done` from the assignee moves `open → answered` and never further; **there is no verb an assignee can send that closes their own item**, which is the whole point of a gatekeeper. A reply of `closed` **from the gatekeeper is honoured** and closes the item. A reply of `closed` **from anyone else posts the reply and moves the item to `answered`** — it is not silently dropped and it is not silently obeyed. **The mail response says which of the two happened**, in one sentence naming the resulting status and, when the sender is not the gatekeeper, who now holds it. A verb that sometimes closes and sometimes does not, without saying so, is how a contractor comes to believe an item is finished when it is sitting in someone else's inbox.

**Decision: inbound identity is bound to a per-recipient HMAC token in the reply address, never to the trivially-forged `From:` header.** The address is §05 §(f)'s format verbatim — **`wi-<short_id>-<hmac10>@in.e-site.live`** — with the HMAC covering `kind|item_id|recipient_user_id` under a server-side secret. Because the address is per recipient, a leaked address grants exactly one person's voice, is revocable on its own (§11.1's offboarding rule revokes it), and identifies the leaker.

**Two different mismatches, two different outcomes, and they must not be conflated.** An HMAC that does not verify, or that resolves to nothing, is **quarantined** — not guessed at, and deliberately not bounced, because a bounce confirms to a forger that the address exists. An **identity** mismatch behind a valid HMAC and a valid DKIM signature — the envelope sender is not the token holder's `public.profiles.email` — is a different case and is **posted** with `result = 'unverified'`, attached to the item, visibly marked as unverified and routed to the Unverified-inbound tray for one-click binding by the PM. Bouncing that class would silence site foremen replying from phone aliases, forwarded mailboxes and shared site addresses, which is exactly the thirteen contractor accounts this section exists to reach. Appendix A(a2) is the authority for both rulings and for every other verdict class.

**Decision: inbound transport is §05's, not a second choice — Cloudflare Email Routing → Worker → the `inbound-email` edge function is primary.** It is free, is available on the current Cloudflare account today, and is provider-independent because the parser consumes raw MIME. **Resend Inbound is adopted only if the Q1 week-1 ticket confirms it retrieves raw MIME and genuinely simplifies attachment handling**; absent that confirmation the Cloudflare path ships as specified and the question is closed. Either way the ingest is a Deno edge function behind a signed webhook, verified exactly the way `auth-email-hook` verifies GoTrue — a `standardwebhooks` `Webhook.verify()` over the raw body with a dedicated edge secret (`apps/edge-functions/supabase/functions/auth-email-hook/index.ts:22`, `:177–180`), deployed `--no-verify-jwt` because the Worker's signature is the authenticator (Appendix A(g), edge functions). **`in.e-site.live` gets its own MX record** so a provider change never touches the sending domain, and no vendor beyond Appendix A(i)'s table is introduced: Cloudflare Email Routing is R0 and transit-only, Resend is already an existing processor.

Ceiling: 25 MB per message, at most 10 attachments, images re-encoded through the same `compressImage` path the web uploader uses (`apps/web/src/lib/image/compress.ts`); attachments land in the destination entity's own bucket under the existing `{org_id}/{project_id}/…` prefix convention (`00091_site_diary_attachments.sql:75–80`). Anything over the ceiling is rejected with a bounce that names the limit, never silently dropped.

⚠ **The inbound handler writes with the service client, which bypasses every RESTRICTIVE policy §11.2 just built — so it must re-resolve authority itself.** The rule: the handler resolves the HMAC to a `user_id`, calls `user_effective_project_role(project_id, user_id)`, and refuses any disposition outside that role's ceiling — which for a `client_viewer` is the §11.1 Watcher row and nothing wider. The service client is used for the *write*, never for the *decision* — **and the decision it reached is recorded in `resolved_role` on the message row (Appendix A(a2)), so an authority call made by a service-role process is auditable after the fact instead of being inferred from its effect.**

**Every message — accepted, refused or quarantined — is recorded in `field.inbound_messages`** (Appendix A(f), Q2, `field` schema), so a rejection is visible rather than invisible: the failure mode that made `sendSiteAssignmentEmail` a known silent hole.

**That table's column set, its single verdict column and its value set are Appendix A(a2)'s, and are cited here rather than restated.** The object had been specified twice — once in §05 §(f) and once in this section — with every shared column renamed, two disposition designs and two rejection vocabularies, inside a document that twice asserts there is one table under one name. A(a2) settles it as one block both sections cite. Four properties of that block are this section's requirements and are named so an implementer knows why they are there: **`resolved_role`**, the authority the handler decided against, without which the ⚠ rule above is a decision made and never recorded; **`result` with `reason` beside it** as the one verdict pair, which is the naming §15 §(b) reads and which replaces the `verification_state` / `reject_reason` pair — the tray predicate is now `result = 'unverified'`; the **typed FKs `work_item_id` and `thread_message_id`** as the disposition link, this section's earlier `(disposition_entity_type, disposition_entity_id)` pair having been deleted as a silent reversal of the anti-polymorphic decision §03 §1.2 and §04 take by name; and `message_id`, `in_reply_to` and `bytes`, carried over because threading a reply to the mail that provoked it, de-duplicating a message delivered twice, and accounting the size ceiling all need them.

**The eight `result` values and the bounce-versus-post ruling for each are A(a2)'s table**, including the two the reply verbs above depend on: `accepted` and `unverified` are both *posted* to the item, and `bounced_access` — a revoked or expired token, a closed item, or a sender who no longer passes `user_has_project_access` — is not. A(a2) also amends §06 §4.1's "a message failing verification is bounced and never posted" to match.

**§15 §(b)'s `inbound_email_events(result, reason)` is this same object under a second name**; there is one table, it is `field.inbound_messages`, and §15's inbound-outcome metric and its abuse/support queue read `result` and `reason` from it. Naming it in `field` rather than `public` keeps it out of a PostgREST-exposed schema that already holds notification and profile data, and it ends its migration with `REVOKE SELECT … FROM anon` verified by `has_table_privilege` — both recorded in A(a2)'s placement note, and `field` being already exposed is why no PostgREST `db_schema` PATCH is involved.

Signature-bearing actions stay behind a session: a SANS 10142-1 record's signatory must be an authenticated identity. That boundary is legal, not technical.

### 11.4 Guest links

No token-share mechanism exists today: the only unauthenticated surfaces are the legal/pricing pages and the QR scan route, which redirects to `/login` before it resolves anything (`(scan)/site/tag/[text]/page.tsx:49–52`). The one account-less write path we do have — unsubscribe keyed on a bare user UUID (`apps/web/src/actions/unsubscribe.actions.ts:8–13`) — is the pattern *not* to copy.

New table `public.guest_links` (Appendix A(f), Q3, `public`): `project_id`, `scope` (CHECK: `timeline | report | snag_visit | form`), `entity_id`, `token_hash` (SHA-256 of a 32-byte CSPRNG token; the token itself is never stored), `email`, `expires_at` (default `now() + 30 days`, with `CHECK (expires_at <= created_at + interval '90 days')` so the hard maximum is a constraint and not a UI convention), `revoked_at`, `max_uses`, `use_count`, `created_by`. **This is the one account-less access mechanism in the programme** — Appendix A(d) records that `projects.report_access_tokens` is not created and that §07's six redemption rules are the properties of this table's `scope='report'`.

**Decision: guest links are read-only by construction.** A `capture` scope was considered and dropped from the CHECK. An account-less write path is a materially different security surface — storage upload, actor attribution against a NULL `audit_log.actor_id` (`00001_initial_schema.sql:127`), and the append-only history — and it collides with §11.3's rule that evidence and signature actions stay behind a session. A guest who needs to contribute gets an account; there is no third state.

**This ruling is the programme's whole position on account-less writing, and other sections cite it rather than re-argue it.** The four `scope` values in the CHECK are read scopes; there is no fifth, in any quarter. Two consequences follow and are recorded where they belong: **§02's mechanic 23 — the account-free guest capture link, the one mechanic in that catalogue that lets someone who has never had an account *originate* work — is not built**, and is retained there as a pattern only; and §09 §(f) cuts the public safety-observation board, the only other account-less write surface anyone proposed, on the same ground and with the same reasoning about a new unauthenticated write path. Nothing in the twelve months creates a project record from an actor with no row in `auth.users`.

**Decision: a guest never holds a Supabase JWT and `anon` is granted nothing.** Redemption is the `/r/[token]` route — ungrouped and unauthenticated per Appendix A(g) — which hashes the presented token, checks expiry, revocation and use count, then reads with the service client behind an explicit column allow-list: the shape `lib/portal/data.ts:13–20` already uses for aspects RLS deliberately blocks. Rate limits are A(d)'s: 20 requests per token per hour and 200 per IP per hour, without disclosing whether the token exists.

⚠ **`public` is a PostgREST-exposed schema, so the new table needs its own lockdown or every signed-in user of every org can read every project's token hashes and guest emails.** Four statements, all required: `ALTER TABLE public.guest_links ENABLE ROW LEVEL SECURITY`; one permissive SELECT policy for `ORG_WRITE_ROLES` on the link's own project (so the settings page can list live links); **no** INSERT/UPDATE/DELETE policy at all, leaving writes to the service client; and `REVOKE ALL ON public.guest_links FROM anon, authenticated` as the backstop. This is the same class as the `anon` SELECT revoke `00168` had to ship after the fact.

A guest sees only the named entity and only in its issued state: a timeline of dated milestones, an issued report, one snag visit, or one form. A guest never sees cost, other projects, the member list, contact details, draft or superseded records, or internal comment threads. Every redemption writes `public.audit_log` with `actor_id = NULL`, `entity_type = 'guest_link'` and the link id, giving a complete answer to "who opened this and when" without inventing a phantom user. Revocation is a single UPDATE and takes effect on the next request — including the bulk revocation §11.1's offboarding rule performs; the project settings page lists live links with their last use.

### 11.5 The client portal rework

The portal today is honest and thin: a mirror-gate shell (`(portal)/layout.tsx:20–22`), a membership check (`lib/portal/data.ts:39–55`), explicit project columns with `contract_value` deliberately absent (`:57–58`), eleven read-only aspect pages, and the standing message "View-only access — contact your project team to request changes" (`(portal)/portal/[projectId]/layout.tsx:37–39`). Four client viewers exist; the last one signed in on 8 July. Read-only with no reason to return is the diagnosis.

**Decision: the portal shell gate is re-cut from the org role onto `user_effective_project_role(project_id)`, and this is a route-structure change, not a predicate swap.** Both current gates resolve a single org-wide role through `getOrgContext()` — `(portal)/layout.tsx:20–22` bounces anyone whose `ctx.role !== 'client_viewer'`, and `requirePortalAccess` repeats the identical org-role check at `lib/portal/data.ts:40–41`. `getOrgContext` returns the caller's *active* org membership, falling back to their oldest (`lib/auth-org.ts:38–69`). The project-scoped client viewers that `00181` exists to recognise therefore cannot reach the portal at all — they land in `(admin)`, which only bounces on the same org-role predicate (`(admin)/layout.tsx:28–29`). Because `(portal)/layout.tsx` has no project id in scope, the gate moves down to a per-project boundary, with `(admin)` bouncing on the same per-project predicate so the mirror stays fail-closed in both directions.

**Decision: that re-cut ships in the SAME PR as the `(work)` route-group split** (Appendix A(g) — `/inbox`, `/my-work` and `/capture` move into a new authentication-only `(work)` group beside `(admin)` and `(portal)`). All three changes — creating `(work)`, moving the portal gate down to a per-project boundary, and re-cutting `(admin)`'s mirror bounce — edit the same two layout files, `(admin)/layout.tsx` and `(portal)/layout.tsx`. Splitting them across PRs means one of the two files carries a half-changed predicate for however long the second PR takes, and a half-changed mirror gate is a lockout for exactly the project-scoped client viewers this work exists to admit. `docs/rbac-matrix.md` and `CONFORMANCE.md` move in that same PR.

This is a change the current data hides. All four live client viewers hold `client_viewer` in the project's *own* org (measured: 4 of 4; zero with no row in the project org, zero with a differing org role), and `active_organisation_id` is NULL on all 36 profiles, so `getOrgContext` always falls through to the single membership. The gate works today by accident. The moment §11.5 asks WM to invite a landlord through the sub-org path — the sanctioned flow `00181` was written for — the portal shell locks them out.

Three additions, all narrow, and **all three land in Q3 (§14 Q3.7), after the report-registry port**. **A live project timeline** — the dated milestone strip plus issued records, the surface CompanyCam monetises as a customer-facing link (`research/01-field-first.md:87`). **Reports** — the existing `projects.reports` list, filtered to issued versions and **gated by the `ReportSpec` registry's `access.read`** (Appendix A(d)), which by Q3 is the single source: `REPORT_KIND_READ_ROLES` and `OPEN_READ_REPORT_KINDS` are deleted by the port and `report-kind-access.contract.test.ts` is repointed at the registry. Writing this gate against the current constant would mean building it twice in one quarter. **Approvals** — the write the Watcher row grants in Q3.

An approval request is a **work item of type `approval`** (Appendix A(a) and A(b) — `approval` is sourceless, registered in Q3, and admitted by `work_items_source_required` alongside `task`) whose assignee is the watcher; `projects.approvals` carries `request_id` referencing that work item, plus `decision`, `comment`, `decided_by`, `decided_at`. "Open" means the work item is not closed. The RESTRICTIVE INSERT policy reads the referenced work item's assignee and status and admits exactly the named approver on an open request, mirroring the `00177` shape. The decision set is §14 Q3.7's — documents and drawings, milestone and beneficial-occupation acceptance, issued reports — and **not variations**, which route to the WM PM. Approving is the reason a landlord opens the app; a portal that cannot accept a decision is a PDF mailing list.

Deliberately not shown, and stated so in the UI rather than merely omitted: contract value, BOQ, rates, valuations, variation orders, cable cost columns, draft QC reports, unissued forms and inspections, internal threads, and any contractor-performance rollup. The reason is commercial, not technical — WM's client is also the contractor's client, and a portal that leaks pricing ends the consultancy relationship.

### 11.6 Onboarding and time-to-value

The invite subsystem was deleted in `00079`; admins create users directly and the recovery flow sets the password (`CONFORMANCE.md:33`). `createUserAction` (`users.actions.ts:41`) creates the auth user with `email_confirm: true`, writes the membership in the same action, then sends a branded link and never blocks on mail. That much is sound. The incident history says the rest was not: a Site URL pointing at a domain with no DNS record, `www.e-site.live` missing from the redirect allowlist, implicit-fragment action links the PKCE client could not consume, and SMTP that had never worked — fourteen invitees stranded, zero completed invites. Those specific defects are fixed. What remains open is measurable in the repo: no copy-link relay when mail fails (`CONFORMANCE.md:41`), invite status derived from a `listUsers` call capped at 1000 users (`:43`), no role explainer for an admin-created member (`:69`), no in-app checklist (`:71`), and no PWA install helper (`:72`).

**Decision: rename "Resend invite" to "Send sign-in link" and let it degrade to a recovery link for users who have already signed in.** `resendInviteAction` today refuses anyone with a non-null `last_sign_in_at` and returns prose telling them to use Forgot password (`users.actions.ts:170–175`) — correct for an invite, useless for the far more common "contractor forgot the URL", which is the actual state of thirteen accounts. The degrade is not new policy: `CONFORMANCE.md:42` already records B6 as ✓ on the evidence "fresh link; recovery-flow degrade per header comment" — a claim the code does not honour. Implementing the degrade makes the conformance row true rather than aspirational.

**Decision: replace the first-run tour with five real work items assigned to the new user at invite time, drawn in order from a fixed candidate list, first five that resolve.** Three of the nine always resolve regardless of project state, so the checklist is never empty and never short:

| # | Candidate work item | Resolves when |
|---|---|---|
| 1 | Acknowledge your assignment to *«project»* | always |
| 2 | **Set the time you want your daily summary** | always — it writes `recap_hour` (§05, range 05–10, default 7) on the user's own notification preferences, which exists from Q1 |
| 3 | Log today's site diary entry | the project has the diary module on (all projects) |
| 4 | Respond to the oldest RFI assigned to you | an RFI exists with `assigned_to` = this user |
| 5 | Take the first RFI on this project that has no owner | an RFI exists with `assigned_to` NULL |
| 6 | Close one open snag on your boards | an open snag exists on a board this user is on |
| 7 | Complete the inspection assigned to you | an `inspections.inspections` row exists at `status='assigned'` for this user |
| 8 | Add one photo to today's diary entry | item 3 has been closed |
| 9 | Confirm your contact details and trade | always (kept as the ninth so it never displaces real work) |

**Item 2 is the recap-hour item, not "Install E-Site to your home screen".** The install item was the original candidate 2 and is **reinstated in Q2**, inserted immediately after item 2 and shifting the rest down by one, because that is when PWA install with web push ships. It is not a Q1 candidate: an item that cannot resolve in the quarter it is offered is worse than no item, and every one of these must resolve for every new user on day one. The recap-hour item replaces it because it always resolves, because the control it writes exists in Q1, and because a user who has chosen their own 07:00 has already decided the daily summary is theirs.

**Items 1, 2 and 9 are sourceless and are created as `item_type='task'`** — the type Appendix A(b) registers in Q1 for exactly this, and one of the two types `work_items_source_required` admits without a source row (Appendix A(a)). They carry no `rfi_id`, `snag_id` or any other source FK, their assignee is the new user and their gatekeeper is the creating admin. The install item added in Q2 is the same shape. Items 3–8 are ordinary mirrored items on real source rows and are never manufactured.

Items 5 and 7 exist because production forces them: `assigned_to` is NULL on **all 15** RFIs, so item 4 can resolve for nobody today and an inbox built only on item 4 would be empty; all 18 inspections sit at `status='assigned'` with zero responses, which is a queue of real first tasks nobody has been pointed at. Item 6 is gated on board membership because all 6 live snags sit on a demo project. On WM's own portfolio — where 6 of 14 projects have a single member and nothing in them — a new user on an empty project still gets items 1, 2, 3, 9 and one of 5/7.

**Activation is defined as: a new user closes any work item inside their first session, where a session is `public.user_sessions` activity with no 30-minute gap (§15 metric 7); `public.auth_events` corroborates and is never the source.** Tracked from Q1, per user. Two things in that sentence are §15 metric 7's decisions, restated here rather than re-taken:

- **The session boundary is `public.user_sessions`, not `public.auth_events`.** `auth_events` is a best-effort *client* call made after an explicit login (`apps/web/src/app/(auth)/login/page.tsx:108`, `:166`), rate-limited per IP (`apps/web/src/actions/auth-event.actions.ts:39`), and it emits nothing at all for a returning cookie session (§15 §(b) row 1). Measured that way, every activation by a cookie-resumed user is invisible and the Q1 target is read off a denominator that omits them. `user_sessions` is written by the single `public.touch_presence(p_platform)` RPC and created in §15's Q1 metrics migration, so it exists from the quarter this metric starts.
- **The numerator is any closed work item, not only one of the five first-run items seeded above.** Items 3–8 of the candidate list are ordinary mirrored rows on real source data, so a user who closes a live RFI in their first session has activated more convincingly than one who ticks a seeded row, and a seeded-only numerator would measure how many seeds survived on an empty project rather than whether the person worked. The first-run-only share is published beside it as a diagnostic, never as the metric.

It is the only onboarding metric that cannot be satisfied by a page view.

Supporting changes: a copy-link fallback beside every invite (B5), a role explainer step (D3), and paginated `listUsers` (B7) — all Q1. The PWA install prompt (D6) becomes a first-run item in Q2, with the install item.

### 11.7 Pricing and packaging

**The live published model is Free / Starter R499 / Professional R1 499 / Enterprise** — four tiers with declared user limits, verified at `packages/shared/src/services/billing.service.ts` (`free` `monthlyKobo: 0`; `starter` `49900` = R499/mo; `professional` `149900` = R1 499/mo; `enterprise` custom) and advertised in exactly those terms at `apps/web/src/app/(public)/pricing/page.tsx:7`. **Any figure of "Pro R999" is wrong and is not what production serves.** Alongside the four tiers sit three one-time or per-seat unlocks (`billing.service.ts:67–89`) and a per-user MV subscription with its own table (`00131:26–38`). Three facts undercut all of it.

**The seat limits are fiction.** `limits.users` is declared in all four plans and read nowhere in the monorepo — a repo-wide grep returns zero call sites. Only `limits.projects` is enforced, at `project.actions.ts:64–72`.

**Nobody has ever bought an unlock.** `billing.org_feature_unlocks`, `billing.org_feature_seats` and `billing.user_mv_subscriptions` are all **empty** in production. Retiring the paywalls removes access from no one.

**No money has ever moved through the marketplace.** `marketplace.paystack_subaccounts` and `marketplace.commission_records` are both **empty**; the two orders are seeded demo rows (`cccccccc-0000-0000-0001-…`, 17 April) with `commission_rate` and `paystack_split_code` NULL.

|---|---|---|---|---|
| **Free** | `free` | 1 | R 0 | — |
| **Practice Solo** | `practice_solo` | up to 3 | R 2 450 | R 24 500 |

Annual is ten months paid for twelve. Every package includes every core module and unlimited participants of every kind. WM at ten active projects sits in **Practice** at R 82 800 a year, against 27 monday.com seats at roughly R 250 each — the comparison the buyer will actually make. Prices stay published on `/pricing`; SMEs cite demo-gated quotes as a reason to walk (`research/01-field-first.md:135`), and every enterprise competitor's dominant complaint is a renewal surprise (`research/02-enterprise.md:67`).

**Decision: price per organisation, banded on active projects — not per project.** Per-project pricing is not buildable on the current stack and the section that proposed it did not say so. `billing.subscriptions` is `UNIQUE (organisation_id)` (`00007_billing_schema.sql:29`) with one fixed `amount_kobo` (`:23`), and the charge path is fixed-amount end to end: `checkout/route.ts:37–42` reads a constant from `PLANS[tier]`, `:54–77` sends either a fixed Paystack Plan code or a fixed one-off `amount`. Paystack Plans carry no quantity dimension, so a monthly figure that varies with project count cannot be billed by the existing subscription flow at all — it would need a new `billing.project_subscriptions` table, a nightly recompute and monthly `transaction/initialize` charges against a stored customer code. Banding buys the same "price the network" property for one migration and no new charging machinery: each band is one Paystack Plan code, one `subscriptions` row, and a band change is a cancel-and-resubscribe on the existing `/api/paystack/cancel-subscription` + checkout pair. **Bands are evaluated only at renewal, never mid-cycle**, so a busy month never produces a surprise charge. **The four bands and this banding decision are the published model; §14's Q4.10 two-package table is amended to them, not the reverse** — the cutover quarter executes this decision and does not re-take it.

The code changes this names, in one PR: a migration widening the `00007:14` tier CHECK to `('free','practice_solo','practice','practice_unlimited')` after re-labelling the two live rows (`starter`/`professional`/`enterprise` are dropped from the CHECK once no row carries them); `PLANS` (`packages/shared/src/services/billing.service.ts:15–55`) re-keyed to the four new tiers with `limits.users` **deleted rather than implemented**, because implementing it would contradict the model; and `checkout/route.ts:8`'s enum re-cut to `z.enum(['practice_solo','practice','practice_unlimited'])`. `checkProjectQuota` (`project.actions.ts:44–76`) is re-pointed from "projects not cancelled" to *active* projects. `/pricing` is republished with the four bands, replacing the Free / Starter R499 / Professional R1 499 / Enterprise list it serves today.

**Decision: an active project is one with a row in a named allow-list of user-authored tables whose `created_at` falls in the last 30 days.** The tables are `projects.site_diary_entries`, `projects.rfis`, `projects.rfi_responses`, `field.snags`, `field.site_forms`, `projects.qc_reports`, `structure.nodes`, `cable_schedule.revisions`, and `projects.work_items`. Notifications, audit rows and system writes are excluded by construction. A nightly job stamps `projects.projects.last_active_at`; the invoice cites one column and one figure, which is the only version of this rule that survives a customer disputing it. "A row written somewhere across 118 tables" is not a definition and would have been a billing argument.

**Decision: retire all four paywalls.** JBCC (R1 999), Inspections (R250), Generator Cost-Recovery (per-seat R2 000) and MV all become included in every paid package. `billing.org_feature_unlocks` and `billing.org_feature_seats` stay as tables and stay honoured — an org holding a row keeps access forever — but no new row can be purchased and the unlock pages redirect to project settings. Because all three tables are empty in production, this strips access from nobody. `public.has_feature` keeps its WM bypass (`00097:49–59`) so nothing about the platform-owner path changes.

**Decision: the declutter is five per-project toggles OFF by default — JBCC, Medium Voltage, Generator Cost-Recovery, Handover and Forms — plus Marketplace removed from navigation entirely.** Appendix A(e) owns the token set, the default state and the write-entry table each RESTRICTIVE policy gates; it is not restated here. Two points belong to this section:

- **Marketplace is not the sixth toggle.** It is org-level — orders key on `contractor_org_id`, not on a project — so there is no project-scoped thing to switch. Both nav entries are deleted and `(admin)/marketplace` redirects to `/inbox` while `NEXT_PUBLIC_PHASE_2_MARKETPLACE` is off; the tables, the seven `(marketplace)` pages and the two April orders are untouched.
- **Inspections stays ON by default; only its R250 paywall dies.** Turning Inspections off would hide the 18 existing `inspections.inspections` rows from the projects that hold them, and those 18 are the queue items §11.6 hands new users.

For the five that do go off, **the enabling migration backfills the toggle ON for every project already holding a row in that module's write-entry table** — `projects.jbcc_notices`, `cable_schedule.mv_study_settings` / `cable_schedule.fault_sources`, `gcr.zones`, `projects.handover_checklist`, `field.site_forms`. A toggle that hides existing work is a data-loss report, not a declutter. **There is no Marketplace backfill row and one must not be added**: `marketplace.orders` carries no `project_id` to backfill against, so the statement is unimplementable rather than merely unnecessary — an implementer who writes it will be looking for a column that does not exist.

**Decision: MV's disclaimer gate survives the paywall's death, and it stops being bypassable.** `public.user_has_mv_access` (`00131_mv_user_subscription.sql:62–71`) today returns TRUE unconditionally for any active member of the WM-Consulting org. Re-cut to test only `disclaimer_accepted_at`, it loses that bypass — deliberately, because a liability acknowledgement the platform owner can skip is not an acknowledgement. One-off consequence, stated plainly so nobody files it as a regression: every current WM MV user sees the disclaimer once, on next use. They are the only MV users; `billing.user_mv_subscriptions` is empty.

**Decision: park the marketplace and change no commission constant — in any quarter.** The 6% figure lives in five places, not the one the draft named — `marketplace-payment/index.ts:29` (`DEFAULT_COMMISSION_RATE`), `paystack-webhook/index.ts:61`, `packages/db/src/services/payment.service.ts:16`, the DDL default `percentage_charge NUMERIC(5,2) NOT NULL DEFAULT 6.00` at `00016_commission_paystack.sql:20`, and a hardcoded `percentageCharge: 94` at `api/paystack/subaccount/route.ts:53`, with a sixth copy in `packages/shared/src/__tests__/commission/commission.test.ts:25`. Changing them would move no money — there is no subaccount, no split code and no commission record in production — and a Paystack split's share is fixed at creation (`marketplace-payment/index.ts:192–206`), so any future rate change means recreating splits anyway. The one-line fix is on the other side: **the public copy is corrected, not the code.** `/pricing` advertises a flat 5% in its metadata (`(public)/pricing/page.tsx:7`), its intro (`:158–159`) and a dedicated section (`:413–494`) for a module that no longer appears in navigation; all four are removed.
