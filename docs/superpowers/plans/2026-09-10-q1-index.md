## Migration numbering

Every plan writes a placeholder number. **Claim the real number at merge, never at branch time**, against
both `max(version)` in `supabase_migrations.schema_migrations` *and* `origin/main`, and announce it to any
concurrent session. `supabase db push` keys on the version **prefix**: a number already in the ledger
makes it print "up to date", exit 0 and skip the file silently. That is how PR #163's migration never
applied behind a green workflow.

**A green *Deploy DB Migrations* run is not evidence a migration ran.** Item 1 builds
`scripts/verify-migration-applied.ts` and the `-- @verify:` header convention for exactly this reason, and
it is on the critical path because the other ten Q1 migrations land behind it.

## Standing rules for every task

- **TDD.** The failing test first, watched failing, then the minimal implementation, then watched passing.
- **The fixture rule.** Ask of any fixture: *what would this have to look like for the test to be able to
  fail?* Prove each new test by breaking the thing it guards. Three shipped defects in this codebase were
  invisible because the fixture could not express the property under test.
- **No metric without its writer in the same migration.** `notifications.read_at`,
  `email_sequence_events.opened_at` and `auth.users.last_sign_in_at` are all columns that look like
  measurements and are not. That pattern does not repeat.
- Every function in an exposed schema: `REVOKE ... FROM PUBLIC` **and** an explicit `REVOKE ... FROM anon`,
  verified with `has_function_privilege`, never by reading `proacl`.
- Never `current_user` for authorisation inside a `SECURITY DEFINER` function.
- Page gating is not a gate. Gate in the app **and** with a RESTRICTIVE database policy.
- `docs/rbac-matrix.md` changes in the same PR as any route or endpoint; `CONFORMANCE.md` for auth changes.
- Verify from the empty state a real user starts in, never a deep link into seeded data.

## Improvements folded in during planning

Each plan carries an **"Improvements folded in"** section and a **"Deferred improvements"** table. Forty-
eight improvements were folded in as real tasks across the four plans. The deferred table in each plan is
the owner's decision list — it is complete and honest about what was left out and why.

The two largest deferred items, both recommended as **separate Q1 items** rather than rejected:

1. **A delivery chip on `/settings/users`** — "Delivered 3 Sep" / "Bounced — permanent" / "No mail sent",
   org-admin gated. Without a surface, the delivery evidence item 0 gathers is a database fact the project
   manager deciding whether to phone a foreman cannot reach. Fund from the pre-window's idle 0.8 weeks,
   cap at 0.3, cut first if item 1 runs long.
2. **A "why is this mine?" explainer** on a work item, showing which resolver step chose the holder. Real
   value once 34 back-filled items land on four people, but it is an Inbox surface change and belongs with
   item 4 or 5.
